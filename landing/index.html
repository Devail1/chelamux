Install

Requires Linux, WSL or macOS · Python ≥ 3.11 · tmux · git · uv · the claude CLI · gh (for the PR flow)

git clone https://github.com/Devail1/chelamux && cd chelamux
uv sync --all-extras
uv run chela status
  1. Log the claude CLI in once (claude, then /login). chela drives it and never handles credentials.
  2. Inside Claude Code, add the hooks plugin that enforces the merge gate: /plugin marketplace add Devail1/chelamux, then /plugin install chela@chela.
  3. Follow Getting started: about 10 minutes from clone to a first agent-opened PR.

Status: early. The core (scheduler, dispatcher, messaging) is solid and tested; the dashboard and live wall ship in the same install. chela is self-hosted and single-user: you run it on your own machine, driving one Claude account (the whole fleet shares its 5h / weekly rate limits).

How it works

From a tracker task to a merged PR, and the one place a human is asked.

  1. 1

    Step 1: Tracker → worktree agent

    A ready task in Linear, GitHub issues or a TODO.md becomes one git worktree, one agent and one PR.

  2. 2

    Step 2: The judge corrupts the code

    For each guard the PR claims, it breaks the code under test and re-runs the suite. A guard that stays green sends the PR back for rework.

  3. 3

    Step 3: chela merge refuses

    …unless the judge said clean on the PR's current head, CI is green and the PR is mergeable. A new push voids the verdict.

    THE GATE
  4. 4

    Step 4: One-tap override, audited

    chela merge --override --reason … asks you. One Telegram tap (or the dashboard) approves it, re-checks head and CI, and records who approved.

The full lifecycle, every command and the rework rules: docs/RUNS.md.

FAQ

Is it safe to run unattended?

Be clear about what is and isn't guarded. Dispatched agents run unsandboxed by default (as your user, with your tools and network) under Claude Code's --permission-mode auto classifier, with no inherited MCP servers and an allowlisted environment. A measured sandbox exists and is opt-in per workflow (agent.sandbox: true in WORKFLOW.md).

What chela does guarantee is the other end, and how much depends on the PR's risk tier. In every tier, a PR that touches an always-human path (the workflow file, CI config, the merge gate itself) merges only with your audited approval. Otherwise chela merge needs green CI and a mergeable PR whose live diff still fits its tier, plus:

Core (the dispatcher, the judge, the merge machinery, agent instructions): a clean judge verdict on its head commit, or your audited approval. The judge corrupts each guard the PR claims and checks its tests turn red. A clean verdict is carried across a head move that touches none of the PR's own files, such as a merge from the base branch (re-stamped, not re-judged).

Standard (product and UI work): no per-PR judge. The agent's hand-in runs lint (when configured) and one full suite, and a nightly sweep then corrupts what merged the same way and files an issue per category of guard that survives. A weak guard there is found after merge, not blocked before it.

Prose (docs, changelog, media): green CI.

The full posture: TRUST_AND_APPROVAL_POSTURE.md.

Does it need an API key?

No. chela never handles credentials: it drives the claude CLI inside your tmux windows, so every agent reuses the one login you made with /login (or claude setup-token on a headless box). The tracker integrations need their own tokens: gh logged in for GitHub, a personal API key for Linear.

Linux, macOS or Windows?

Linux and macOS natively. On Windows, run it inside WSL, because chela is built on tmux, which has no native Windows build.

How is it different from Claude's built-in agents?

Claude Code's Agent view and the desktop app are great at running and watching many sessions, and chela runs those same Claude Code sessions. What chela adds is the part after “done”: tracker-driven dispatch into worktrees, a mutation-testing judge whose verdict is bound to the PR head, and a merge command that refuses without it. See Why chela.
